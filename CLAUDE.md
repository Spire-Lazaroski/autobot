# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A strategy lab and paper-trading bot for Alpaca. It backtests the strategies in `autobot/strategies.py` on Alpaca bars, runs a train/test parameter search, and runs the chosen strategies as paper-trading "jobs" from `config.yaml`. See `README.md` for the user-facing overview.

## Commands

Windows, with the venv at `.venv` (created by `start.bat`). Use `.venv/Scripts/python` or activate the venv first.

```
start_lab.bat                                   # strategy lab: API + web, opens http://127.0.0.1:5190
.venv/Scripts/python -m api                     # lab API only, 127.0.0.1:$API_PORT (8710); no auto-reload (uvicorn's reloader hangs here), restart after backend edits
cd web && npm run dev                           # lab web only, 127.0.0.1:$WEB_PORT (5190), proxies /api and /ws
cd web && npx tsc --noEmit                      # typecheck the web app
.venv/Scripts/python -m pytest -q tests         # all tests; single test: pytest tests/test_api.py::test_compare
.venv/Scripts/pip install -r requirements.txt
.venv/Scripts/python run_backtest.py --demo     # CLI backtest + search on synthetic data (no keys)
.venv/Scripts/python run_backtest.py            # same on real Alpaca data (needs .env); writes results/*.csv
.venv/Scripts/python live.py --once             # one bot tick against the PAPER account, then exit
.venv/Scripts/python live.py --flatten          # close every paper position
```

There is no linter config. `run_backtest.py --demo` is the quickest end-to-end check of `strategies` → `backtest` without network access. `tests/test_no_lookahead.py` recomputes every registered strategy on truncated data and must pass for any new strategy. Ports come from `.env` (`API_PORT`, `WEB_PORT`); 8000/8001 are used by other things on this machine, and everything binds to 127.0.0.1 only. Anything touching `live.py` needs real paper keys in `.env` (`ALPACA_API_KEY`, `ALPACA_SECRET_KEY`).

## Architecture

- **Lab (`api/` + `web/`)**: FastAPI wraps the `autobot` package; it never reimplements backtest logic. Slow work (search, walk-forward) runs through `api/jobs.py` (thread pool, poll `GET /api/jobs/{id}`). Bars are cached in memory per request key on top of `data_cache/`. The web app is React + Vite + Tailwind v4 (custom classes used with `@apply` must be declared with `@utility`), TanStack Query, Plotly via `react-plotly.js/factory`, and lightweight-charts v5 (`chart.addSeries(LineSeries, opts, paneIndex)`, `createSeriesMarkers`). Times cross the API as UTC unix seconds and are shown in New York time.
- **Brand (Spire Analytics, light theme)**: colours are defined only in `web/src/theme.ts` (the 8 brand tokens copied verbatim from the git-ignored `branding/BRAND.md`, plus profit/loss and a few derived UI shades). `npm run brand` (in `web/`) generates `web/src/brand.css`, `autobot/assets/brand.css` (reports, SOP) and `autobot/assets/brand.json` (Python charts, indicator overlay colours); `npm run brand -- --check` fails if they are stale. `tests/test_brand.py` checks the tokens against BRAND.md, the generated files, and WCAG AA for every text colour. Never use gold as text on white. The header CSS in `web/scripts/brand-base.css` is copied rule for rule from the pricing engine's `spire_header.html`. Tailwind colour names (`bg`, `panel`, `fg`, `muted`, `up`, `down`, `warn`, `accent`) map onto the brand variables in `index.css`; charts use `lib/chart.ts` (`C`, the Plotly `spireTemplate`, `DIVERGING`).
- **Indicators** (`autobot/indicators.py`): causal indicator math shared by strategies and charts. `PLOTS[name]` says what the candle view draws for a strategy (overlays on price, extra panes with guide levels); add one when adding a strategy.
- **Strategy contract** (`autobot/strategies.py`): a strategy is `f(df, allow_short=False, **params) -> pd.Series` of target positions (1 / 0 / -1) aligned to `df.index`. The signal on bar t may use data through bar t's close. To add one, write the function and register a `StrategySpec` in `STRATEGIES` with `defaults` and an optional `grid` (the search space). Everything else (the dashboard tabs, CLI, search, live jobs) discovers strategies through `STRATEGIES` and calls them via `get_signal()`. Use the helper `_state_machine` for entry/exit-style strategies and `_apply_side` to drop shorts when `allow_short=False`.
- **No look-ahead lives in the backtester, not the strategy**: `run_backtest` shifts positions by one bar before applying returns. Strategies must not shift their own output forward. Costs are `(fee_bps + slippage_bps)` per unit of turnover.
- **Parameter search** (`parameter_search`): runs the full backtest once per param combo, then splits results at `train_frac`. It ranks on train and reports test. `_valid()` rejects combos where `fast >= slow` or `exit >= entry`; extend it if a new grid has similar constraints. The `_params` column carries the raw dict (dropped before display/CSV) and is what the dashboard copies into a new live job.
- **Meta-strategies** (`autobot/meta.py`, imported by `autobot/__init__.py` so they always register): `regime_switch`, `perf_rotation`, `ensemble_vote` are ordinary strategies (family `meta`) whose params name other strategies. Each underlying strategy runs on full history and the meta layer picks whose signal to use per bar, so switching costs only arise through position turnover. Meta-strategies can't be nested (`_check`). `StrategySpec.explain` returns the per-bar active label that the candle view band and `/api/shift` timeline use. `tests/test_meta.py` plants a future price shock and asserts earlier decisions don't change.
- **Why-logging and reports**: `autobot/decisions.py` builds decision / regime / switch / event records. `Context` computes, once per symbol and bar, the signal, the strategy in charge, the regime (`classify_regimes` with the job's own settings for `regime_switch`, defaults otherwise) and the indicator values, taken from the same `PLOTS` code that draws chart overlays so reports match the charts. Reason sentences are fixed templates filled from those numbers at decision time. `live.py` appends to `logs/decisions.jsonl` every bar via `Recorder` (wrapped in `_safe` so logging can never stop trading); backtests produce the same records with `backtest_decisions`. `autobot/report.py` turns records, fills (Alpaca or backtest) and equity into a self-contained Spire-branded HTML (matplotlib SVG charts) plus PDF via headless Edge; all wording comes from `autobot/plain.py` (shared with the SOP) and fixed rules, and a missing reason is printed as "reason not recorded". `python -m autobot.report --backtest --demo ...` or `--date YYYY-MM-DD`.
- **Walk-forward** (`walk_forward` in `backtest.py`): windows are cut on the first symbol's bar clock. Every grid combo is backtested once on full history (valid only because strategies are causal), then each window picks the best combo on its train slice and the chosen effective positions are stitched and replayed with `_replay`, so a parameter switch at a window boundary pays costs. `tests/test_walk_forward.py` checks that appending future bars never changes earlier choices.
- **Data** (`autobot/data.py`): `fetch_bars` caches to `data_cache/{SYM}_{tf}_{days}d_{YYYYMMDD}.csv.gz` (crypto `/` → `-`), keyed by end date, so a cache is reused for the whole day. The RTH filter (9:30–16:00 NY) is applied after loading and only to non-crypto intraday bars. The default feed is `iex` (free). A symbol containing `/` is treated as crypto everywhere (`is_crypto`).
- **Live bot** (`live.py`): calls the private helpers `_download` and `_keys` from `autobot.data` directly and bypasses the cache. It ticks a few seconds after each bar boundary, drops the still-forming bar, recomputes the full signal on ~300 bars of history (more if the job's strategy has `warmup_days`, see `liveconfig.warmup_days`), and trades the difference between target and current qty with market orders. Constraints the code relies on:
  - `TradingClient(..., paper=True)` is intentionally hard-coded in `live.py` and `api/live.py`. Do not add a live-money path; `tests/test_live.py` checks it.
  - `config.yaml` is re-read at every bar (`Bot.reload_config`, mtime-based). Changes are validated with `autobot/liveconfig.validate_live` (the same function the API's `PUT /api/config` uses), logged as `CONFIG ...` lines and kept in `status.json`; an invalid config is rejected and the previous one stays. A symbol dropped from all enabled jobs has its position closed.
  - Single-bot lock: the run loop writes `logs/bot.pid` (pid + heartbeat) every poll. `liveconfig.bot_state()` treats a bot as running only if the pid is alive *and* the heartbeat is fresh. `pid_alive` queries the process via Win32 APIs; never use `os.kill(pid, 0)` on Windows, which terminates the process.
  - Hang protection: alpaca-py sets no request timeout, so every client must go through `autobot.data.with_timeout` (a half-closed socket once blocked the bot for hours, ignoring STOP). The `_watchdog` thread has its own client: it writes the heartbeat only while the main loop progresses (`_progress`), takes over an unhandled STOP file after 10 s, enforces the loss limit while the loop is stuck, and after `stall_seconds` (default 300) logs CRITICAL and exits without trading. `tests/test_hang.py` covers this.
  - `Bot(cfg, tc=...)` accepts an injected broker client, and logging is only set up in `main()`, so tests import `live` without touching Alpaca or `logs/bot.log`.
  - A symbol may belong to only one enabled job, because Alpaca nets positions per symbol (`validate_live` enforces it).
  - Crypto positions come back from Alpaca without the slash (`BTC/USD` → `BTCUSD`, see `_pos_key`). Crypto can't be shorted and uses fractional qty with GTC orders; stocks use whole shares with DAY orders.
  - Flipping long↔short is sent as two orders.
  - Risk: the daily-loss limit (measured against `last_equity`) flattens and halts; stocks are flattened N minutes before the close.
- **Dashboard ↔ bot coupling** (`api/live.py`): the lab never signals or kills the bot process. It writes `config.yaml` (applied at the bot's next bar), starts `live.py` as a detached subprocess (`/api/live/start` refuses while `bot_state()` says one is running), and stops it by creating the `STOP` file (`/api/live/stop` requires `{"confirm": true}`), which the bot polls, then flattens and exits. It shows state from `logs/status.json`, `logs/trades.csv`, `logs/bot.log` and read-only Alpaca calls; `/ws/live` pushes one shared, cached snapshot every 3 s. `PUT /api/config` rewrites `config.yaml` with `yaml.safe_dump`, so comments in that file are lost when the Jobs editor saves.
